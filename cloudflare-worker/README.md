# SentinelX Cloudflare API Gateway

Authenticated gateway between the GitHub Pages frontend and the existing Activepieces GUI read workflows, with encrypted integration configuration storage. This branch uses a small custom analyst login instead of Cloudflare Access, so it does not require a Zero Trust subscription or Access application.

## Security model

- The GUI authenticates with a dedicated analyst password sent only to `POST /api/auth/login`.
- The Worker verifies a PBKDF2-SHA-256 password hash; the plaintext password is never stored in Worker configuration.
- Successful login receives a four-hour signed, HttpOnly, Secure, SameSite=None, Partitioned session cookie.
- Session signatures use a separate `SESSION_HMAC_SECRET` Worker secret.
- Login attempts are rate-limited (5 per minute per IP and Cloudflare location; Cloudflare's rate limiter is approximate).
- CORS is restricted to `https://aiman0x.github.io` and credentialed requests only.
- Activepieces bridge key remains a Worker secret and is never sent to the browser.
- Data retrieval is GET-only. The only write endpoint in this phase saves encrypted integration configuration; case updates, playbook execution, connection tests, and defensive actions are not exposed.
- This is a single shared analyst login, not multi-user identity management. Use a unique, strong password and rotate it if shared.

## Authentication endpoints

- `POST /api/auth/login` with JSON `{"password":"..."}` sets the session cookie.
- `GET /api/auth/me` reports whether the cookie is valid.
- `POST /api/auth/logout` clears the cookie.

The browser must call the API with `credentials: "include"`. The cookie uses the Partitioned attribute because the GitHub Pages frontend and workers.dev API are on different sites. Browser third-party-cookie/privacy settings may still affect cookie behavior and must be checked during integration testing.

## Worker variables and secrets

Add these non-secret variables in Workers & Pages > sentinelx-api-gateway > Settings > Variables and Secrets:

- `ALLOWED_ORIGIN` = `https://aiman0x.github.io`

Add these as **Secret** values, not plaintext variables:

- `LOGIN_PASSWORD_HASH` = PBKDF2-SHA-256 encoded hash in the format `pbkdf2-sha256$310000$BASE64URL_SALT$BASE64URL_HASH`
- `SESSION_HMAC_SECRET` = a separately generated random secret (at least 32 random bytes, encoded as hex)
- `CONFIG_ENCRYPTION_KEY` = a separate 32-byte random AES-256-GCM key (64 hex characters), generated by the local PowerShell helper
- `AP_BRIDGE_KEY` = the rotated `X-SentinelX-Bridge-Key` value configured on all eight Activepieces read workflows
- `AP_READ_DETECTION_FINDINGS_URL`, `AP_READ_INCIDENT_RECORDS_URL`, `AP_READ_INVESTIGATIONS_URL`, `AP_READ_EVIDENCE_REFERENCES_URL`, `AP_READ_AUDIT_LOGS_URL`, `AP_READ_ASSETS_URL`, `AP_READ_DETECTION_RULES_URL`, and `AP_READ_SECURITY_INTEGRATIONS_URL` = the corresponding published Activepieces webhook URLs with `/sync` appended

Do not reuse the telemetry ingestion key. Do not put any secret or Activepieces webhook URL in GitHub source, Vite variables, or browser code. The INTEGRATION_CONFIGS KV namespace stores tool configuration encrypted with AES-256-GCM; the encryption key stays in Worker Secrets. Secret fields are never returned to the browser.

Copy each webhook URL from its corresponding published Activepieces workflow trigger, then append `/sync` to the URL path so the Worker waits for the flow's Return Response step. The Catch Webhook trigger accepts GET, and each flow's Return Response step returns the table data as JSON. Confirm its auth check expects the bridge key header before enabling live data. Do not guess URLs.

## Integration configuration

- POST /api/integrations/{id}/config saves allowlisted configuration fields after analyst authentication.
- Supported IDs: wazuh, sysmon, clamav, yara, suricata, zeek. ActivePieces webhook URLs and bridge credentials are configured only as Worker Secrets.
- Values are encrypted before being written to the dedicated INTEGRATION_CONFIGS KV namespace.
- GET /api/integrations includes only safe non-secret configuration values and configured field names; passwords and webhook secrets are never returned.
- Connection-test routes deliberately return an unavailable response until each tool-specific Activepieces adapter and health-check workflow is implemented. A saved configuration is not a connected integration.

## Deployment

The repository includes `.github/workflows/deploy-worker.yml`. After this PR is merged to `main`, it can deploy the separate `sentinelx-api-gateway` Worker when Worker files change, or be started manually from GitHub Actions.

### GitHub Actions deployment prerequisites

- Add `CLOUDFLARE_API_TOKEN` as a GitHub Actions secret. Grant only the Cloudflare permissions needed to deploy Workers Scripts for this account.
- Add `CLOUDFLARE_ACCOUNT_ID` as a GitHub Actions repository/environment variable.
- The workflow deploys only `cloudflare-worker/wrangler.toml`; it does not deploy or modify the existing `medicoreiph` Worker.

### Worker runtime configuration

1. Run `scripts/generate-auth-secrets.ps1` locally and add its three outputs as Worker Secrets. The password is chosen locally and is never sent to GitHub or this repository.
2. Add `ALLOWED_ORIGIN` = `https://aiman0x.github.io` as a Worker variable.
3. Add the eight Activepieces webhook URL secrets copied from their published trigger settings, with `/sync` appended.
4. Rotate the shared bridge credential on all eight Activepieces read workflows, then set the matching value as `AP_BRIDGE_KEY` in Worker Secrets. Keep it separate from the Windows telemetry ingestion key.
5. Deploy the Worker through the GitHub Actions workflow. Runtime routes remain unavailable until the required Worker secrets are configured.
6. After the Worker is deployed and its exact workers.dev URL is confirmed, set the GitHub repository variable `VITE_API_BASE_URL` to that URL and publish the GUI.
7. Verify browser session-cookie behavior and actual Activepieces response shapes before enabling live dashboard data.

A successful `/health` endpoint is intentionally not provided: only the authentication and actual data endpoints should be used to validate the deployed gateway.
